# Database Schema --- Offline-First Ebook Reader

**Document version:** 1.0\
**Date:** 7 November 2026\
**Status:** Proposed schema\
**Database:** SQLite via Drift (Dart)\
**Platforms:** Android first, iOS second

------------------------------------------------------------------------

## 1. Purpose

This document defines the local relational data model for the
offline-first ebook reader. It is the implementation reference for Drift
tables, relationships, indexes, migrations, and data-access behavior.

The database stores **application metadata and reading state**. EPUB and
PDF publication files are stored separately in app-private file storage.
Publication bytes must never be stored as SQLite BLOBs.

The schema is designed to: - Work without an account, backend, or
network connection. - Preserve a user's library, collections, progress,
bookmarks, and EPUB highlights. - Support portable manual backup and
restore. - Keep EPUB and PDF location data extensible without coupling
the database to a specific reader-plugin class. - Be shared by Android
and iOS through the same Flutter/Dart implementation.

## 2. Design principles

1.  **SQLite is the source of truth** for structured library data.
2.  **Files live outside SQLite** in app-private storage.
3.  Use stable UUID identifiers generated by the application.
4.  Store timestamps as UTC Unix epoch milliseconds (`INTEGER`).
5.  Store reader-engine locators as serialized JSON strings, not plugin
    objects.
6.  Keep format-specific location details in a flexible locator payload
    while exposing common fields for queries and UI.
7.  Use foreign keys and transactions for relational integrity.
8.  Use explicit Drift schema migrations; never delete a database to
    work around a migration failure.
9.  Prefer normalized relational data for relationships. JSON is
    acceptable for small structured metadata such as author lists and
    reader locator payloads.
10. Avoid duplicating values that can be derived, unless the duplicate
    is an intentional performance or snapshot field.

## 3. Database overview

### 3.1 Tables

  -----------------------------------------------------------------------
  Table                               Purpose
  ----------------------------------- -----------------------------------
  `books`                             One record per imported publication

  `reading_progress`                  Latest saved reading position for
                                      each book

  `bookmarks`                         User-created saved locations

  `highlights`                        EPUB text selections, colors, and
                                      notes

  `collections`                       User-created library collections

  `collection_books`                  Many-to-many relationship between
                                      collections and books
  -----------------------------------------------------------------------

The MVP does not require a separate reading-session/history table.
`books.last_opened_at` is sufficient for a "Recently opened" section.
Add a session table only if the product later needs reading-time
analytics, session history, or daily reading statistics.

### 3.2 Relationship diagram

``` text
books
  │
  ├── 1 : 1 ── reading_progress
  │
  ├── 1 : N ── bookmarks
  │
  ├── 1 : N ── highlights
  │
  └── N : M ── collections
                 │
                 └── collection_books
```

`collection_books` is the join table connecting `books` and
`collections`.

## 4. Conventions and data types

  Concept         SQLite representation                  Dart representation
  --------------- -------------------------------------- --------------------------------
  UUID            `TEXT`                                 `String`
  Required text   `TEXT NOT NULL`                        `String`
  Optional text   `TEXT NULL`                            `String?`
  Boolean         `INTEGER` (`0` or `1`)                 `bool`
  UTC timestamp   `INTEGER` epoch milliseconds           `DateTime`
  File size       `INTEGER` bytes                        `int`
  Progression     `REAL` from `0.0` to `1.0`, nullable   `double?`
  JSON payload    `TEXT`                                 Typed Dart model after parsing

### 4.1 Identifier rules

-   Generate UUID v4 identifiers in the application before inserting
    records.
-   IDs must remain stable across backup and restore.
-   Do not use a title, filename, file path, or database auto-increment
    value as the public identity of a book.
-   Preserve IDs during restore when there is no conflict.
-   Define explicit conflict handling when restoring a record whose ID
    already exists.

### 4.2 Timestamp rules

-   Store all timestamps in UTC epoch milliseconds.
-   Convert to local time only when presenting dates to the user.
-   Use `created_at` and `updated_at` consistently.
-   Update `updated_at` whenever a user-visible record changes.

## 5. Table definitions

## 5.1 `books`

Stores publication metadata and the relative path to the app-private
publication file.

  `description`       TEXT                               Yes Optional

                                                             as supplied; not

  `format`            TEXT                                No `epub` or `pdf`

  `file_path`         TEXT                                No Relative path

  `cover_path`        TEXT                               Yes Relative path to

  `file_size_bytes`   INTEGER                             No Must be greater

                                                             imported file

  `reading_status`    TEXT                                No `unread`,
                                                             `reading`,
                                                             `finished`;
                                                             default `unread`

  `added_at`          INTEGER                             No UTC epoch
                                                             milliseconds

  `last_opened_at`    INTEGER                            Yes UTC epoch
                                                             milliseconds

  `updated_at`        INTEGER                             No UTC epoch
                                                             milliseconds

  `metadata_json`     TEXT                               Yes Optional source
                                                             metadata not
                                                             represented by
                                                             columns
  ---------------------------------------------------------------------------

**Constraints** - `title` must not be empty after trimming. - `format`
must be one of `epub`, `pdf`. - `reading_status` must be one of
`unread`, `reading`, `finished`. - `file_size_bytes` must be positive. -
`file_checksum` must contain a SHA-256 digest. - `file_path` must be a
relative path and must not contain path traversal segments. -
`file_path` should be unique while a publication is in the library. -
`file_checksum` should be indexed, but should not be globally unique:
users may intentionally import duplicate copies or editions.

**Drift notes** - Use a text column for `authors_json`, with a Dart
converter that validates JSON and returns `List<String>`. - Prefer a
typed enum converter for `format` and `reading_status`, while retaining
stable serialized values. - Do not store a reader-plugin publication
object in `metadata_json`.

## 5.2 `reading_progress`

Stores the latest restorable location for a book. There should be at
most one current progress row per book.

  ------------------------------------------------------------------------
  Column           Type                             Null? Constraints /
                                                          notes
  ---------------- ---------------- --------------------- ----------------
  `book_id`        TEXT                                No Primary key; FK
                                                          to `books.id`

  `locator_json`   TEXT                               Yes Serialized
                                                          Readium locator
                                                          or app-owned
                                                          locator payload

  `page_number`    INTEGER                            Yes One-based page
                                                          number when
                                                          meaningful,
                                                          primarily PDF

  `progression`    REAL                               Yes Approximate
                                                          normalized
                                                          progression,
                                                          range 0.0--1.0

  `updated_at`     INTEGER                             No UTC epoch
                                                          milliseconds
  ------------------------------------------------------------------------

**Rules** - `book_id` is both primary key and foreign key. - A progress
row may not exist until a user first opens a book. - `locator_json` is
the preferred restoration source when available. - `page_number` and
`progression` are supplementary display/index fields, not universal
restoration keys. - `progression` must be null or between `0.0` and
`1.0`. - For EPUB, persist the complete serialized locator returned by
Readium, including its CFI/location and text context when supplied. -
For PDF, persist the reader's stable page/location data. Do not assume
every PDF implementation uses the same locator shape. - If the reader
engine changes, parse the old locator through a versioned
migration/adapter rather than silently discarding it.

**Progress write policy** - Debounce high-frequency page/scroll
events. - Save after meaningful navigation, after a short period of
inactivity, on app backgrounding, and when closing the reader. - Do not
rely solely on an app-close event; the operating system can terminate
the process without delivering one. - Update `books.reading_status` to
`reading` when the book is opened, unless it is already `finished`. -
Mark a book `finished` only through an explicit product rule, such as
the reader reporting completion or the user marking it finished. Avoid
marking it finished from a noisy percentage threshold alone.

## 5.3 `bookmarks`

Stores user-created saved locations in a publication.

  Column           Type        Null? Constraints / notes
  ---------------- --------- ------- ------------------------
  `id`             TEXT           No Primary key; UUID
  `book_id`        TEXT           No FK to `books.id`
  `locator_json`   TEXT           No Serialized location
  `label`          TEXT          Yes Optional user label
  `created_at`     INTEGER        No UTC epoch milliseconds
  `updated_at`     INTEGER        No UTC epoch milliseconds

**Rules** - A bookmark must reference an existing book. - Store the
complete locator, not only a page number or percentage. - The UI may
display a page label or chapter title derived from locator metadata, but
that derived display text need not be stored in the MVP. - A user can
create multiple bookmarks at the same location unless product design
explicitly chooses deduplication. - Deleting a book cascades to its
bookmarks.

## 5.4 `highlights`

Stores EPUB text selections and optional user notes.

  -----------------------------------------------------------------------------
  Column            Type                             Null? Constraints / notes
  ----------------- ---------------- --------------------- --------------------
  `id`              TEXT                                No Primary key; UUID

  `book_id`         TEXT                                No FK to `books.id`

  `locator_json`    TEXT                                No Serialized
                                                           selection/location

  `selected_text`   TEXT                               Yes Selected text, if
                                                           supplied

  `color`           TEXT                                No Stable app color
                                                           token or validated
                                                           color value

  `note`            TEXT                               Yes Optional user note

  `created_at`      INTEGER                             No UTC epoch
                                                           milliseconds

  `updated_at`      INTEGER                             No UTC epoch
                                                           milliseconds
  -----------------------------------------------------------------------------

**Rules** - MVP highlights are supported for EPUB only, subject to the
capabilities verified in the reader integration spike. - PDF text
highlighting and advanced PDF annotation are out of MVP. - Store the
locator required to reapply the highlight through the reader engine's
annotation/decorator API. - `selected_text` is for display/search
convenience; the locator remains the source for restoring the
selection. - Use app-owned color tokens such as `yellow`, `green`,
`blue`, and `pink`, rather than coupling stored data to a specific theme
palette. - Deleting a book cascades to its highlights.

## 5.5 `collections`

Stores user-created groups of books.

  Column         Type        Null? Constraints / notes
  -------------- --------- ------- ------------------------
  `id`           TEXT           No Primary key; UUID
  `name`         TEXT           No Trimmed; non-empty
  `created_at`   INTEGER        No UTC epoch milliseconds
  `updated_at`   INTEGER        No UTC epoch milliseconds

**Rules** - Collection names are user-editable. - Whether duplicate
collection names are allowed should be a product decision. Recommended
MVP behavior: allow them. - Deleting a collection must not delete its
books.

## 5.6 `collection_books`

Join table for the many-to-many relationship between collections and
books.

  Column            Type        Null? Constraints / notes
  ----------------- --------- ------- ------------------------
  `collection_id`   TEXT           No FK to `collections.id`
  `book_id`         TEXT           No FK to `books.id`
  `added_at`        INTEGER        No UTC epoch milliseconds

**Constraints** - Composite primary key: (`collection_id`, `book_id`). -
Deleting a collection cascades to its join rows. - Deleting a book
cascades to its join rows. - A book can belong to multiple collections.

## 6. Indexes

Create indexes for common library and relationship queries.

  -------------------------------------------------------------------------------
  Index                           Columns                 Purpose
  ------------------------------- ----------------------- -----------------------
  `idx_books_title`               `title`                 Title lookup and
                                                          sorting

  `idx_books_added_at`            `added_at`              Recently added

  `idx_books_last_opened_at`      `last_opened_at`        Recently opened

  `idx_books_status`              `reading_status`        Filter by reading
                                                          status

  `idx_books_format`              `format`                Filter by format

  `idx_books_checksum`            `file_checksum`         Duplicate detection

  `idx_bookmarks_book_created`    `book_id`, `created_at` Book's bookmarks

  `idx_highlights_book_created`   `book_id`, `created_at` Book's highlights

  `idx_collection_books_book`     `book_id`               Find collections
                                                          containing a book
  -------------------------------------------------------------------------------

The `collection_books` composite primary key already indexes lookups
beginning with `collection_id`. Add the `book_id` index for reverse
lookups.

### 6.1 Search

For a small MVP library, use indexed/normalized title and author queries
with SQLite `LIKE` or equivalent Drift expressions. `LIKE` may not use
an ordinary index for a leading-wildcard search.

Consider SQLite FTS5 in a later iteration if full-text search across
title, author, description, and notes becomes a requirement. FTS5
availability and tokenizer behavior must be verified on both platform
SQLite builds before adoption.

## 7. Referential integrity and deletion behavior

Enable SQLite foreign-key enforcement for every database connection.

  -----------------------------------------------------------------------
  Parent deletion                     Child behavior
  ----------------------------------- -----------------------------------
  Delete a book                       Delete its progress, bookmarks,
                                      highlights, and collection links

  Delete a collection                 Delete its collection links; keep
                                      books

  Delete a highlight                  No other records affected

  Delete a bookmark                   No other records affected
  -----------------------------------------------------------------------

### 7.1 Book deletion is a file-system workflow

SQLite cannot transactionally delete a file. Implement book deletion as
a recoverable workflow:

1.  Mark the book as pending deletion in an application-level operation
    or move its files into a temporary trash/staging directory.
2.  Delete the relational book row in a database transaction;
    foreign-key cascades remove dependent rows.
3.  Delete the staged file(s).
4.  If the database transaction fails, restore the files to their
    original location.
5.  If file deletion fails after the database transaction, retain a
    cleanup record or retryable orphan-file entry and retry later.

For the simplest MVP implementation, a dedicated
`pending_file_operations` table is optional. If the implementation uses
a staging/trash folder, startup reconciliation can detect and clean up
abandoned operations. Do not silently leave files behind indefinitely.

### 7.2 Remove from library vs delete file

The product must define the distinction clearly: - **Remove from
library:** remove the database record and dependent reading data. The
app-owned copy may be deleted after confirmation. - **Delete publication
file:** remove the app-owned copy and its library record. Explain that
reading progress, bookmarks, and highlights for that book will also be
removed unless the product explicitly supports retaining orphaned
metadata.

Do not present two actions that behave identically under different
names.

**MVP decision:** the app owns only its private copy of each publication,
so there is a single **Remove from library** action. It deletes the record,
its dependent reading data and the app's copy, following §7.1 (files are
moved to `staging/` first and moved back if the database delete fails). The
user's original source document is never modified or deleted.

## 8. Drift implementation guidance

### 8.1 Suggested Drift table layout

Use one Drift table class per table. Keep generated `*.g.dart` files out
of manual edits.

Example conceptual declaration:

``` dart
class Books extends Table {
  TextColumn get id => text()();

  TextColumn get title => text()();

  TextColumn get authorsJson =>
      text().withDefault(const Constant('[]'))();

  TextColumn get format => text()();

  TextColumn get filePath => text()();

  IntColumn get fileSizeBytes => integer()();

  TextColumn get fileChecksum => text()();

  TextColumn get readingStatus =>
      text().withDefault(const Constant('unread'))();

  IntColumn get addedAt => integer()();

  IntColumn get lastOpenedAt => integer().nullable()();

  IntColumn get updatedAt => integer()();

  @override
  Set<Column> get primaryKey => {id};
}
```

This is illustrative, not a complete production table declaration. Add
all columns, checks, references, indexes, and custom constraints
according to the final Drift version and project conventions.

### 8.2 Database class

-   Create a single application database provider.
-   Use the platform-appropriate SQLite opening strategy supported by
    Drift.
-   Keep database creation and migration code centralized.
-   Do not open a new database connection for each repository call.
-   Ensure the database connection is closed during test teardown and
    app shutdown where appropriate.
-   Configure foreign keys and any required SQLite pragmas through the
    supported Drift connection setup.

### 8.3 Repository boundaries

Suggested repositories:

``` text
BookRepository
  - watchBooks()
  - getBook(bookId)
  - addBook(book)
  - updateBookMetadata(book)
  - updateReadingStatus(bookId, status)
  - removeBook(bookId)

ReadingProgressRepository
  - getProgress(bookId)
  - saveProgress(progress)
  - clearProgress(bookId)

BookmarkRepository
  - watchBookmarks(bookId)
  - addBookmark(bookmark)
  - updateBookmark(bookmark)
  - deleteBookmark(bookmarkId)

HighlightRepository
  - watchHighlights(bookId)
  - addHighlight(highlight)
  - updateHighlight(highlight)
  - deleteHighlight(highlightId)

CollectionRepository
  - watchCollections()
  - createCollection(collection)
  - renameCollection(collectionId, name)
  - deleteCollection(collectionId)
  - addBookToCollection(collectionId, bookId)
  - removeBookFromCollection(collectionId, bookId)
```

Repositories should return domain models, not Drift-generated row
classes. Keep database-specific types and converters in the data layer.

## 9. Locator serialization contract

Do not store `flutter_readium` or native Readium objects directly in
Drift.

Store the serialized locator JSON supplied by the reader adapter. Also
define an application-owned envelope so the app can identify the source
and serialization version.

Illustrative envelope:

``` json
{
  "schemaVersion": 1,
  "engine": "readium",
  "engineLocatorVersion": null,
  "format": "epub",
  "locator": {
    "href": "chapter-01.xhtml",
    "type": "application/xhtml+xml",
    "locations": {},
    "text": {}
  }
}
```

The `locator` contents above are illustrative. The adapter must preserve
the actual serialized locator structure returned by the pinned
reader-engine version. Do not invent or normalize away fields that
Readium needs for restoration.

Rules: - Validate JSON before saving. - Preserve unknown locator fields
when round-tripping where possible. - Keep the app envelope version
separate from the database schema version. - Add migration logic when
the app changes its own locator envelope. - If a locator cannot be
restored, keep the book and other annotations intact and show a
recoverable message rather than deleting the saved data.

## 10. Database migrations

Use Drift's `schemaVersion` and migration strategy.

### Initial schema

`schemaVersion = 1`

Create: - `books` - `reading_progress` - `bookmarks` - `highlights` -
`collections` - `collection_books` - all foreign keys, constraints, and
indexes.

### Migration policy

1.  Increase the schema version for every incompatible schema change.
2.  Write an explicit migration from each supported prior version.
3.  Test migration from a real database fixture created by the previous
    app version.
4.  Never use destructive migration in production.
5.  Back up or preserve user data before any migration that rewrites
    locator or publication metadata.
6.  Keep migration operations transactional where SQLite/Drift supports
    it.
7.  Add tests for both successful migrations and failure handling.

Example:

``` dart
@override
int get schemaVersion => 1;

@override
MigrationStrategy get migration => MigrationStrategy(
  onCreate: (Migrator m) async {
    await m.createAll();
  },
  onUpgrade: (Migrator m, int from, int to) async {
    // Add explicit versioned migrations here as schema evolves.
  },
);
```

Do not add empty migration branches for future versions. Add a migration
only when the schema actually changes.

### Schema snapshots

Each released schema version is exported to `drift_schemas/` (for example
`drift_schema_v1.json`). Before raising `schemaVersion`, keep the previous
snapshot and export the new one:

``` bash
dart run drift_dev schema dump lib/data/database/app_database.dart drift_schemas/
```

Migration tests for version *n* start from the snapshot of each earlier
version. Version 1 has no earlier version, so no migration test exists yet.

## 11. Backup and restore mapping

The backup format is specified separately in `BACKUP_FORMAT.md`. The
database schema maps to the archive as follows:

  -----------------------------------------------------------------------
  Database data                       Backup inclusion
  ----------------------------------- -----------------------------------
  `books`                             Always

  `reading_progress`                  Always

  `bookmarks`                         Always

  `highlights`                        Always

  `collections`                       Always

  `collection_books`                  Always

  Publication files                   Full backup only

  Cover files                         Include if present; otherwise
                                      regenerate where possible

  App preferences                     Include only selected portable
                                      preferences
  -----------------------------------------------------------------------

Do not export internal database implementation details such as SQLite
row IDs or Drift-generated metadata. Export stable app-owned records and
IDs.

### 11.1 Restore transaction

-   Parse and validate the backup before modifying the live database.
-   Map archive records into app-owned domain/data models.
-   Copy publication files into a staging area.
-   Validate file sizes and checksums.
-   Apply the database import transaction.
-   Move validated files into final storage.
-   If any step fails, restore the previous database state and clean up
    staged files.

The restore implementation must define duplicate and conflict behavior
in `BACKUP_FORMAT.md`.

## 12. Data integrity and reconciliation

The application should run lightweight integrity checks at appropriate
times, not on every screen render.

Examples: - A `books.file_path` entry points to a missing file. - A
publication file exists but has no database record. - A cover path is
missing. - A progress row contains invalid locator JSON. - A collection
link references a deleted book or collection. - A checksum does not
match the stored publication file.

Suggested reconciliation: 1. On startup or library maintenance,
enumerate known book files. 2. Compare known paths with database
records. 3. Report missing files and offer a remove/relink recovery
path. 4. Clean abandoned staging files only after a safe age threshold
and confirmation rules. 5. Do not automatically delete unknown files
that may be in-progress imports or backups.

## 13. Testing requirements

### Unit tests

-   Enum and JSON converters.
-   Author-list serialization.
-   Locator envelope serialization and validation.
-   Repository mapping between Drift rows and domain models.
-   Duplicate import policy.

### Database tests

-   Insert, update, query, and delete each entity.
-   Foreign-key cascade behavior.
-   Composite key uniqueness for `collection_books`.
-   Progression range validation.
-   Invalid enum values rejected by application validation.
-   Index-relevant query behavior.
-   Database close/reopen persistence.
-   Migration from each supported prior schema version.

### Workflow tests

-   Import creates a book row only after file validation succeeds.
-   Failed import removes staged files.
-   Deleting a book removes its dependent rows.
-   Failed deletion does not leave an unrecoverable file/database
    mismatch.
-   Full restore preserves relationships and locators.
-   Library-only restore does not claim that missing publication files
    are present.
-   Restore failure leaves the pre-restore library usable.

## 15. Definition of done

The database implementation is ready when:

-   All six tables are implemented in Drift.
-   Foreign keys, constraints, and indexes are present.
-   All timestamps follow the UTC epoch-millisecond convention.
-   Book files are stored outside SQLite.
-   EPUB and PDF positions can be persisted and restored.
-   Bookmarks and EPUB highlights survive app restarts.
-   Collection membership is correctly maintained.
-   Deleting a book follows a recoverable file/database workflow.
-   Database migrations are tested.
-   Backup export/import can preserve all records and relationships.
-   The same database schema and repository behavior work on Android and
    iOS.

**Schema decision summary:** Use Drift/SQLite for books, reading
progress, bookmarks, EPUB highlights, collections, and collection
membership. Store imported publications in app-private files. Store
serialized, versioned Readium locator data rather than reader-plugin
objects. Use explicit migrations, foreign-key constraints, and
recoverable workflows for file/database operations.
